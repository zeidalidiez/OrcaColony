Report 002Partial evidence · method revision needed

Persistent block workers cut repeated download 85.95%; quality recovers only 21.49%.

Across 12 authenticated TinyStories assignments, rolling one of six blocks at a time improved held-out loss monotonically by 0.301125. The full-model control improved by 1.401365 on the same batches and optimizer-step count. Worker tensor residency was 57.58% lower, but the comparison also exposed a schedule mismatch that the next P5 topology must remove.

The systems case strengthened; the training case did not.

Persistent shared state materially reduces repeat transfer, and every deterministic measurement reproduced exactly. But sequential one-block updates train only 11.44% of full parameters per step and use a shallow objective that is not the full model's objective.

Decision Keep P5 active. Replace sequential rotation with one block-sharded global step before scaling.
01 / Question

Does the T0 memory result survive authenticated data and held-out evaluation?

The coordinator retained a six-block, 6,901,760-parameter model. One persistent worker session loaded shared token, position, normalization, and output state once, then replaced only the selected block as assignments rotated 0 → 1 → 2 → 3 → 4 → 5 twice.

Training consumed the exact campaign-bound TinyStories bundle at revision 99e5642…. Both rolling and replicated controls started from identical weights, saw the same 12 training batches, used coordinator-owned AdamW, and were evaluated on the same frozen 16 validation sequences every two steps.

04 / Reproduction

Numerical evidence repeated exactly; operational observations formed a narrow range.

  • +
    Every deterministic field matched.

    Both runs produced the same seven loss pairs, byte counts, block sequence, dataset revision, and rolling/full final model SHA-256 identities.

  • +
    Rolling training work was about 3.0× faster.

    The measured rolling section—including exact shared-cache admission—took 1.962–2.078 seconds versus 5.974–6.225 seconds for full-model training. This is expected because far fewer parameters and blocks execute; it is not an end-to-end throughput claim.

  • !
    Evaluation dominated the combined process.

    Two models evaluated every two steps, taking 16.478–16.941 of 26.972–27.927 total seconds. A real campaign would choose a less intrusive cadence.

  • !
    Peak RSS is combined-process evidence.

    The isolated CLI process peaked between 700,350,464 and 705,372,160 bytes while simultaneously retaining rolling coordinator, full baseline, worker session, optimizers, and dataset tensors. It is not worker-only RSS.

05 / Interpretation

The 21.49% quality ratio is diagnostic—not a fair production contest.

At each control step, AdamW updates the full model: six blocks plus shared embedding and normalization state. At each rolling step, it updates one block, or 11.44% of the full parameters. Equal optimizer-step and batch counts therefore do not mean equal parameter-update coverage.

The objective differs too. Every selected block receives token embeddings directly and feeds the shared output path directly, regardless of where that block belongs in the full model. Its shallow-model gradient is not the corresponding slice of the full-model gradient.

This remains a 12-step, randomly initialized 6.9M-parameter CPU experiment over 16 validation sequences. It proves real-data trajectory and systems behavior, not useful story generation, public-worker operation, or final training quality.

06 / Next iteration

Make a global step from a complete set of block workers.

The next P5 slice should assign one fixed block to each of six persistent workers against the same checkpoint and batch, collect all six mapped gradients, and apply one coordinator AdamW step. That gives every block one update per global step while preserving the low individual-worker residency measured here.

Worker-to-block affinity also changes the unique-transfer result: one worker can cache shared state plus one block instead of rotating through the entire model. The report must show individual, aggregate, cold, warm, download, and upload bytes separately. If quality still lags after schedule normalization, the following control should test exact boundary activations or gradient targets to isolate the shallow-objective error.

This P5 work proceeds independently of the slower, manually reviewed bug-report → triage JSON campaign and does not block P6/P7 pre-building.
