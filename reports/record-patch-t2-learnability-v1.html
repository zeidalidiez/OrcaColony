TASK GATE FAILED · NO COMMUNITY CAMPAIGN STARTED

Language loss fell 83%. Exact patch execution stayed at zero.

After 128 centralized CPU updates, the T2 model generated JSON-shaped records on every public case, but every record repeated an object key. The predeclared learnability gate correctly rejected the checkpoint.

The recipe learned structure, not the task.

Step 128 was selected only by public language loss. It scored 0/32 exact, 0/32 semantic, and 0/32 strict valid JSON. No community compute or task-model promotion is justified by this result.

At step 128 all 32 outputs began with { and ended with }. All 32 were syntactically object-shaped but repeated at least one key, which the frozen evaluator rejects. This is measured structural movement. It is not exact patch execution, semantic correctness, or valid output under the task contract.

Why the zero is retained: ordinary JSON parsers often keep the last duplicate key, but Record Patch v1 forbids that ambiguity. Relaxing the evaluator after seeing these outputs would change the task and turn a failed gate into a post hoc success.

The first 128 steps consumed 512 of 4,618 packed training sequences and 262,144 of 2,364,891 packed token positions. The proposed 2,048-step campaign would cover about 1.774 packed-sequence epochs. This bounded check stopped after roughly 6.25% of the proposed updates.

Training loss decreased overall, but the early path was not smooth. Public validation improved after step 1, regressed above initialization at step 8, then recovered strongly by steps 32 and 128. Gradient clipping was active on 89.1% of updates. Those facts make insufficient exposure and aggressive early optimization plausible explanations, not proven causes.

Prompt loss did not explain away the result

The all-token objective spends loss weight on both the prompt and answer. At step 128 the prompt mean loss was 1.4527 and the answer mean loss was 2.0935. Answer loss still improved by 7.0239 points from initialization, and answer-token accuracy reached 40.7%. Training therefore affected the answer distribution, but it had not produced one complete correct answer.

A target-only objective could be more sample-efficient, but this run did not test it. The first follow-up should continue the same checkpoint and optimizer so that exposure is changed without also changing the objective, learning rate, data order, or decoding policy.

What follows from this result

  1. Do not request volunteer compute for the current checkpoint yet.
  2. The exposure-only continuation has now been completed through step 512. See Report 012.
  3. Because exact behavior remained at zero, test answer-only loss next while keeping the model, data, order, optimizer, learning rate, decoding, and evaluator fixed.
  4. Keep both reserved holdouts closed until checkpoint selection under a campaign that has actually passed its public learnability gate.
