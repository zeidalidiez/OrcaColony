# Campaign tiers and immutable historical names

New capability campaigns use the tier ladder in `SPEC.md`:

| Tier | Approximate parameters | Default role |
| --- | ---: | --- |
| T0 | 1.3M | deterministic fixture |
| T1 | 6.9M | browser and systems proof |
| T2 | 17.5M | first useful narrow-capability campaign |
| T3 | 46.7M | larger specialization candidate |
| T4 | 111M | browser/native boundary |

The existing `t2-tinystories-memory-*.json` campaigns contain 91,544,064
parameters. They predate the finalized tier ladder and are retained under their
original names because their IDs and byte hashes are part of committed research
evidence. Treat them as the **legacy 91M memory-stress profile**, not as the T2
capability tier. Do not copy that label into new campaigns.

## Torch backend identities

The default development lock uses PyTorch's official CPU index. Current Python
tests use `t0-lora-smoke-cpu.json`, whose base identity was frozen with
PyTorch 2.13.0+cpu.

`t0-lora-smoke.json` remains unchanged because it is part of earlier P2
research evidence created with a different PyTorch wheel build. It is a
historical artifact, not a portable seed recipe. Do not replace either digest
with one generated by another backend. Training campaigns must publish the
exact Python, Torch version, wheel build, backend, and initialized weight
identity they used.

System-proof campaigns may omit promotion-only fields. A model intended for
public capability claims must use the capability-campaign contract documented in
`SPEC.md`: a concrete use case, executable objective, baseline, repeated
validation, disjoint reserved language-loss holdout, frozen behavioral
final-holdout suite, guardrails, contributor-credit policy, licenses, and
Hugging Face destinations.

## Participant and credit manifests

Use `orcacolony_participants_v2` for new campaigns; see
`participants-v2.example.json`. Its worker IDs and token hashes form the
campaign-locked authentication revision. Public name/pseudonym/anonymous,
profile, team, roles, totals, and hardware choices form a separate credit
revision. An operator can update only those v2 credit fields and reload the
coordinator before release without changing worker authority. The release then
freezes the selected choices in `attribution-snapshot.json` and
`CONTRIBUTORS.md`.

Legacy v1 participant files keep their original all-fields-locked revision for
historical recovery compatibility.

## First true-T2 capability campaign

`record-patch-t2-v1.json` freezes the 17,538,816-parameter Record Patch campaign,
packed dataset hashes, disjoint language-loss ranges, behavioral suite and
evaluator revisions, initialization identity, thresholds, guardrails, licenses,
and private-first `OrcaColony/record-patch-t2-v1` and
`OrcaColony/record-patch-v1` destinations.

The real participant manifest is intentionally absent. Create it from
`record-patch-t2-participants.example.json`, keep worker tokens outside Git, and
complete the credit choices before accepting work. Do not start this campaign
until the bounded centralized learnability check passes review.
